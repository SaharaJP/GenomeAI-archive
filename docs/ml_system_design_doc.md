# ML System Design Doc
## Дизайн ML системы - GenomeAI AgroAnimals MVP

> **Контекст проекта:** MVP для рынка СНГ, домен — молочный КРС, целевая задача — продуктивность.  
> **Ключевой артефакт MVP:** ML-скоринг + AI-отчёт с рекомендациями (decision-support) в локальном контуре (on-prem).

---

### 1. Цели и предпосылки

#### 1.1. Зачем идем в разработку продукта?

- **Бизнес-цель**  
  Повысить качество и скорость управленческих решений по продуктивности стада (отбор «материнского ядра», приоритеты осеменения, кандидаты на выбраковку) на промышленных фермах СНГ за счёт стандартизированного ML-скоринга и автоматизированного AI-отчёта.

- **Почему станет лучше, чем сейчас, от использования ML**  
  Сейчас решения часто принимаются вручную (Excel + эксперт), что приводит к:
  - несопоставимости групп (ошибка сравнения «разных условий»),
  - высокой доле ошибок данных (ID/даты/аномалии),
  - высокой трудоёмкости и низкой повторяемости подхода по площадкам холдинга.  
  ML позволяет **стандартизировать оценку** и **учесть ключевые факторы** (как минимум parity/период/площадка/возраст), а AI-отчёт переводит результаты в понятные действия и фиксирует решения.

- **Что считаем успехом итерации с точки зрения бизнеса**  
  Итерация успешна, если на пилоте:
  1) отчёт выпускается **регулярно** (минимум 2–3 прогона),  
  2) по отчёту фиксируются **решения** (минимум 3 решения на цикл),  
  3) улучшается **качество данных** (снижение критических ошибок P0 между итерациями),  
  4) руководство принимает формат отчёта (Executive 1 стр. + полная версия) и готово обсуждать коммерческий контракт.

---

#### 1.2. Бизнес-требования и ограничения

- **Краткое описание БТ и ссылки на детальные документы**  
  - MVP должен выпускать **AI-отчёт** с рекомендациями и приложением таблиц (Executive + Full).  
  - В MVP **обязателен ML**, а не только «правила»/z-score, обусловлено дальнейшим масштабированием.  
  - Источники данных: выгрузки из учётных систем/Excel (P0), опционально расширение P1.  
  - Режим исполнения: **on-prem по умолчанию**.

- **Бизнес-ограничения**
  - Не делаем «официальную племенную оценку» и не заявляем эквивалентность государственным/ассоциативным индексам.  
  - Запрещены обещания гарантированного прироста продуктивности без пилотной валидации.  
  - В отчёте рекомендации — строго **decision-support**: финальное решение за специалистом/хозяйством.  
  - Данные хозяйства — коммерчески чувствительные: нужен NDA и контроль контура хранения.

- **Что ожидаем от конкретной итерации**
  - UC-1 (P0): рейтинг продуктивности + списки действий + AI-отчёт.  
  - UC-3 (P0): отчёт качества данных и план улучшений.  
  - UC-2 (P0): режим «готовность к mating plan» (gap analysis) — без обязательного построения полноценного плана спариваний.

- **Описание бизнес-процесса пилота**
  1) Хозяйство выгружает P0-данные (lactations) за 12–24 месяца.  
  2) Система выполняет QC, обучает/валидирует модель (если применимо), считает скоринг.  
  3) Генерируется AI-отчёт (Executive + Full) и таблицы.  
  4) Главный зоотехник/селекционер ревьюит, фиксирует решения.  
  5) На следующем цикле — повтор + измерение прогресса качества данных и стабильности выводов.

- **Что считаем успешным пилотом?**
  - Принятие отчёта как регулярного инструмента управления.  
  - Прозрачность: метрики качества ML + ограничения данных.  
  - Практичность: отчёт приводит к конкретным действиям (ядро/приоритет/выбраковка).  
  - Возможные пути развития: добавление P1 (ECM/FPCM, SCC, test-day), затем mating plan P1 при наличии родословной.

---

#### 1.3. Что входит в скоуп проекта/итерации, что не входит

- **На закрытие каких БТ подписываемся в данной итерации**
  - ML-модель для оценки/прогноза milk_305_kg (или скоринга) на уровне лактации, с time-split оценкой качества.
  - Генерация fact pack (проверенные агрегаты/факты) для LLM.
  - Генерация AI-отчёта по шаблону с анти-галлюцинационными правилами.
  - QC и флаги качества данных, влияющие на confidence рекомендаций.

- **Что не будет закрыто**
  - Полноценный mating plan P1 без родословной и справочника быков.
  - Онлайн-инференс в режиме «почти real-time» (оставляем batch).
  - Автоматические интеграции со всеми учётками и гос-системами (только файлы/выгрузки на MVP).
  - Продвинутая модель по здоровью/репродукции (только флаги при наличии данных).

- **Результат с точки зрения качества кода и воспроизводимости**
  - Воспроизводимый запуск пайплайна по шагам: Raw→Canonical→QC→ML→Scoring→FactPack→Report.
  - Версионирование: data_version / model_version / report_template_version / run_id.
  - Полный набор артефактов прогона сохранён и привязан к run_id (для аудита).

- **Планируемый технический долг**
  - Частичная автоматизация маппинга выгрузок разных учётных систем (на MVP допустим ручной mapping-конфиг).
  - Полноценный мониторинг дрейфа в проде (в MVP — базовая проверка стабильности распределений).
  - Масштабирование на десятки хозяйств без ручной поддержки (в MVP допускается сопровождение).

---

#### 1.4. Предпосылки решения

- **Предпосылки по данным**
  - P0-минимум: `animal_id`, `parity`, `calving_date`, `milk_305_kg` (+ `site` при нескольких площадках).
  - Горизонт: **не прогноз “в будущее на N месяцев”**, а оценка/скоринг по доступным лактациям и стандартная сопоставимость групп.
  - Гранулярность: **лактация** (одна строка = одна лактация животного).

- **Предпосылки по бизнес-логике**
  - Сравнение корректно только внутри **contemporary group**: площадка/ферма + период (год/квартал) + parity.
  - Рекомендации формируются на пересечении: QC-флаги + ML-скоринг + бизнес-правила (пороги/минимальные размеры групп).

- **Предпосылки по эксплуатации**
  - Batch-режим пересчёта: ежемесячно/ежеквартально (на пилоте) → затем возможно еженедельно.
  - On-prem хранение и выполнение; внешние вызовы допустимы только после согласования ИБ/юристов.

### 2. Методология 

#### 2.1. Постановка задачи

- **Основная задача MVP:** прогноз/скоринг продуктивности `milk_305_kg` на уровне лактации и построение ранжирования животных/лактаций внутри сопоставимых групп.  
- Тип задачи: **регрессия + ранжирование** (и последующая генерация рекомендаций как decision-support).  
- Дополнительная задача: **оценка качества данных (QC) и confidence** выводов модели.

---

#### 2.2. Блок-схема решения
Добавлена в формате картинки

**Архитектура бейзлайна** (для сравнения на пилоте):  
QC → расчет z-score внутри contemporary group → отчет (без ML прогнозной модели, но с теми же артефактами QC и отчёта).  
В MVP отличие существенное: **ML обязателен** и даёт прогноз/остатки + метрики качества.

---

#### 2.3. Этапы решения задачи

Ниже описаны этапы **для бейзлайна** и **для основного MVP** с учетом результатов EDA (см. артефакты в репозитории).

**Артефакты EDA:**
- `eda/eda_public.ipynb` — воспроизводимый EDA на публичном суррогатном датасете (Zenodo).
- `eda/eda_report.md` — краткий отчет с выводами.
- `eda/figs/*.png` — визуализации, используемые в отчете.

---

##### Этап 1 — Подготовка данных (EDA + витрины/таблицы)

**Цель этапа:** получить валидированный датасет (train/inference) и минимальную витрину признаков, пригодную для бейзлайна и основной модели.

**1) Данные и сущности**

- Основная сущность MVP: **запись по лактации** (одна строка на «животное × лактация»).
- Ключ записи (естественный): `(farm/site, animal_id, parity, calving_date)`.

**P0 (минимум для MVP):**

| Поле | Тип | Обязательно | Комментарий |
|---|---:|:---:|---|
| `farm` / `site` | cat | ✅ | Идентификатор площадки/фермы (особенно важно для холдингов) |
| `animal_id` | str | ✅ | Стабильный ID животного внутри хозяйства |
| `parity` | int | ✅ | Номер лактации |
| `calving_date` | date | ✅ | Дата отёла |
| `milk_305_kg` | float | ✅ | Удой за 305 дней (целевая переменная) |

**P1 (желательно, но не обязательно для старта):** `birth_date`, `fat_pct`, `protein_pct`, `scc`, test-day записи, pedigree (`sire_id`, `dam_id`) и т.д.

**2) Итоги EDA и выявленные проблемы (переносимые требования к QC)**

На демо-данных были намеренно «смоделированы» типовые проблемы, которые ожидаемо встречаются в реальных выгрузках:

- **Дубликаты** по естественному ключу (несколько строк на одну лактацию). *(на демо: 47 строк-дубликатов)*
- **Невалидные значения**: `milk_305_kg <= 0`, `parity` вне диапазона 1..12. *(на демо: 23 и 23 строк соответственно)*
- **Невалидные даты**: `calving_date` «из будущего» относительно даты выгрузки. *(на демо: 4 771 строк > 2025-12-20)*
- **Пропуски** в показателях качества молока (`fat/protein/SCC`) — существенные доли пропусков → эти поля не делаем обязательными для P0. *(на демо: fat 18%, protein 22%, SCC 28%)*

**Риски, которые нужно учесть на пилоте:**
- Разные правила расчёта `milk_305_kg` и округления (шум/смещение лейбла).
- Несогласованные единицы измерения и форматы (десятичные разделители, кодировки, локали дат).
- Нестабильность идентификаторов (перенос животного между площадками, смена ID).
- Недостаточная история (слишком короткий период → слабая обобщаемость).

**3) Процесс генерации/поступления данных (как это будет в MVP)**

- Источник: выгрузки из учётных систем ферм (**СЕЛЭКС/1С/Excel**), иногда несколько файлов на разные сущности.
- Формат: CSV/XLSX (часто с локальными форматами дат/чисел).
- Периодичность (для MVP): **batch** — 1 раз в месяц/квартал (или по запросу на пилоте).
- Путь: выгрузка → защищённый канал передачи → загрузка в on‑prem контур → QC → витрины/фичи → скоринг → отчёт.

**4) Если данных не достаточно — как решаем**

Минимум для стабильной оценки модели:
- ≥ **24 месяцев** истории (чтобы увидеть сезонность/дрейф),
- ≥ **5k лактаций** (желательно больше, 20–50k для уверенного обучения),  
- обязательно наличие `farm/site`.

Если данных мало:
- начинаем с **бейзлайна** (средние по parity/ферме/сезону),
- объединяем несколько площадок/ферм с обязательным `farm_id` и мониторингом смещения,
- расширяем P1-признаки (возраст при отёле, пред. лактация, test-day ряд) как ускоритель качества.

**5) Конфиденциальность и безопасность**

- Данные о животных и производственные показатели — **коммерческая тайна** хозяйства.
- В MVP предполагается **on‑prem**, контроль доступа и шифрование хранения/бэкапов.
- Персональные данные сотрудников не нужны и должны исключаться из выгрузок.

**6) Результат этапа**
- Валидированный датасет (train/inference), дедуплицированный и приведённый к единому формату.
- QC отчёт (ошибки, пропуски, аномалии, период покрытия).
- Витрина признаков P0/P1 (как минимум `farm`, `parity`, признаки сезонности из `calving_date`).

##### Этап 2 — Подготовка прогнозных моделей (бейзлайн + основной MVP)

**Цель этапа:** построить модель(и), которые предсказывают **ожидаемый `milk_305_kg`** и формируют понятный скоринг отклонений.

**1) Метрики и loss**

- Основная ML‑метрика: **MAE (кг)** — робастна к выбросам и хорошо интерпретируема для бизнеса.
- Дополнительно: **RMSE** (штрафует большие ошибки), **MAPE** (аккуратно, с отсечением малых значений).
- Для оценки “скоринга” (decision‑support): доля животных в нижнем квантиле скоринга, которые фактически попадают в нижний квантиль по `milk_305_kg` (после появления факта).

Loss (в зависимости от модели):
- L1 / MAE или **Huber** (компромисс между MAE и RMSE).
- Опционально: **Quantile loss** для оценки интервалов неопределённости (P10/P50/P90).

**2) Схема валидации**

Т.к. есть сезонность и дрейф:
- **Time-based split**: train на прошлом, valid/test на будущем.
- Rolling/expanding window (например, train до T, valid на T+3 месяца).
- Отчёт метрик по срезам: `farm`, `parity`, сезон.

Anti‑leakage:
- В признаки нельзя включать данные, которые появляются **после** момента, когда делаем прогноз (особенно test‑day, если прогноз делаем “на старте лактации”).

**3) Бейзлайны (обязательны)**

1. `mean_global`: глобальное среднее `milk_305_kg`.
2. `mean_by_parity`: среднее по `parity`.
3. `mean_by_parity_farm`: среднее по (`farm`, `parity`) — это минимально приемлемый бейзлайн для холдингов.
4. (Опц.) линейная модель на `parity` + сезонность (month sin/cos).

**4) Основная модель MVP (план)**

Предпочтительно: градиентный бустинг по деревьям (CatBoost/LightGBM/XGBoost), т.к.:
- хорошо работает на табличных данных,
- устойчив к неидеальным распределениям,
- удобно интерпретируется через важности признаков.

Минимальный набор фичей (P0):
- `parity`
- `farm` (категория)
- признаки сезонности из `calving_date` (месяц/квартал, sin/cos)

Расширение (P1+):
- возраст при отёле (`age_at_calving`),
- пред. лактация (`prev_milk_305`, `delta_to_prev`),
- агрегаты test‑day (первые 30–60 дней),
- события здоровья/репродукции,
- погода/THI.

**5) Интерпретация**
- глобальная важность признаков (permutation importance),
- частные зависимости (PDP) для ключевых фичей,
- (для tree‑моделей) SHAP на уровне записи — в он‑прем контуре при необходимости.

**6) Риски этапа и снижение**
- Ограниченные фичи P0 → потолок качества: снижаем ожидания, делаем упор на скоринг отклонений и объяснения.
- Неоднородность ферм → обязательно `farm_id` + отчёт метрик по фермам.
- Выбросы/ошибки ввода → QC + робастные loss/обрезка хвостов.
- Лейбл‑шум (`milk_305` считается по-разному) → описать правило расчёта и валидировать на пилоте.

**7) Результат этапа**
- Зафиксированный бейзлайн + протокол валидации.
- Выбранная основная модель MVP + отчёт метрик/срезов.
- Механика формирования скоринга (например: `index = actual / predicted`, `residual = actual - predicted`, + доверительный интервал).
