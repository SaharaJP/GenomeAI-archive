# ML System Design Doc - [RU]
## Дизайн ML системы - GenomeAI AgroAnimals MVP

> **Контекст проекта:** MVP для рынка СНГ, домен — молочный КРС, целевая задача — продуктивность.  
> **Ключевой артефакт MVP:** ML-скоринг + AI-отчёт с рекомендациями (decision-support) в локальном контуре (on-prem).

---

### 1. Цели и предпосылки

#### 1.1. Зачем идем в разработку продукта?

- **Бизнес-цель**  
  Повысить качество и скорость управленческих решений по продуктивности стада (отбор «материнского ядра», приоритеты осеменения, кандидаты на выбраковку) на промышленных фермах СНГ за счёт стандартизированного ML-скоринга и автоматизированного AI-отчёта.

- **Почему станет лучше, чем сейчас, от использования ML**  
  Сейчас решения часто принимаются вручную (Excel + эксперт), что приводит к:
  - несопоставимости групп (ошибка сравнения «разных условий»),
  - высокой доле ошибок данных (ID/даты/аномалии),
  - высокой трудоёмкости и низкой повторяемости подхода по площадкам холдинга.  
  ML позволяет **стандартизировать оценку** и **учесть ключевые факторы** (как минимум parity/период/площадка/возраст), а AI-отчёт переводит результаты в понятные действия и фиксирует решения.

- **Что считаем успехом итерации с точки зрения бизнеса**  
  Итерация успешна, если на пилоте:
  1) отчёт выпускается **регулярно** (минимум 2–3 прогона),  
  2) по отчёту фиксируются **решения** (минимум 3 решения на цикл),  
  3) улучшается **качество данных** (снижение критических ошибок P0 между итерациями),  
  4) руководство принимает формат отчёта (Executive 1 стр. + полная версия) и готово обсуждать коммерческий контракт.

---

#### 1.2. Бизнес-требования и ограничения

- **Краткое описание БТ и ссылки на детальные документы**  
  - MVP должен выпускать **AI-отчёт** с рекомендациями и приложением таблиц (Executive + Full).  
  - В MVP **обязателен ML**, а не только «правила»/z-score.  
  - Источники данных: выгрузки из учётных систем/Excel (P0), опционально расширение P1.  
  - Режим исполнения: **on-prem по умолчанию**.  
  См. внутренние документы проекта:  
  - Док.1: процессы AS-IS/TO-BE + юридика  
  - Док.3: юзкейсы MVP (UC-1/UC-2/UC-3)  
  - Док.4: источники данных и data request pack  
  - Док.5: пайплайны и артефакты

- **Бизнес-ограничения**
  - Не делаем «официальную племенную оценку» и не заявляем эквивалентность государственным/ассоциативным индексам.  
  - Запрещены обещания гарантированного прироста продуктивности без пилотной валидации.  
  - В отчёте рекомендации — строго **decision-support**: финальное решение за специалистом/хозяйством.  
  - Данные хозяйства — коммерчески чувствительные: нужен NDA и контроль контура хранения.

- **Что ожидаем от конкретной итерации**
  - UC-1 (P0): рейтинг продуктивности + списки действий + AI-отчёт.  
  - UC-3 (P0): отчёт качества данных и план улучшений.  
  - UC-2 (P0): режим «готовность к mating plan» (gap analysis) — без обязательного построения полноценного плана спариваний.

- **Описание бизнес-процесса пилота**
  1) Хозяйство выгружает P0-данные (lactations) за 12–24 месяца.  
  2) Система выполняет QC, обучает/валидирует модель (если применимо), считает скоринг.  
  3) Генерируется AI-отчёт (Executive + Full) и таблицы.  
  4) Главный зоотехник/селекционер ревьюит, фиксирует решения.  
  5) На следующем цикле — повтор + измерение прогресса качества данных и стабильности выводов.

- **Что считаем успешным пилотом?**
  - Принятие отчёта как регулярного инструмента управления.  
  - Прозрачность: метрики качества ML + ограничения данных.  
  - Практичность: отчёт приводит к конкретным действиям (ядро/приоритет/выбраковка).  
  - Возможные пути развития: добавление P1 (ECM/FPCM, SCC, test-day), затем mating plan P1 при наличии родословной.

---

#### 1.3. Что входит в скоуп проекта/итерации, что не входит

- **На закрытие каких БТ подписываемся в данной итерации**
  - ML-модель для оценки/прогноза milk_305_kg (или скоринга) на уровне лактации, с time-split оценкой качества.
  - Генерация fact pack (проверенные агрегаты/факты) для LLM.
  - Генерация AI-отчёта по шаблону с анти-галлюцинационными правилами.
  - QC и флаги качества данных, влияющие на confidence рекомендаций.

- **Что не будет закрыто**
  - Полноценный mating plan P1 без родословной и справочника быков.
  - Онлайн-инференс в режиме «почти real-time» (оставляем batch).
  - Автоматические интеграции со всеми учётками и гос-системами (только файлы/выгрузки на MVP).
  - Продвинутая модель по здоровью/репродукции (только флаги при наличии данных).

- **Результат с точки зрения качества кода и воспроизводимости**
  - Воспроизводимый запуск пайплайна по шагам: Raw→Canonical→QC→ML→Scoring→FactPack→Report.
  - Версионирование: data_version / model_version / report_template_version / run_id.
  - Полный набор артефактов прогона сохранён и привязан к run_id (для аудита).

- **Планируемый технический долг**
  - Частичная автоматизация маппинга выгрузок разных учётных систем (на MVP допустим ручной mapping-конфиг).
  - Полноценный мониторинг дрейфа в проде (в MVP — базовая проверка стабильности распределений).
  - Масштабирование на десятки хозяйств без ручной поддержки (в MVP допускается сопровождение).

#### 1.4. Предпосылки решения

- **Предпосылки по данным**
  - P0-минимум: `animal_id`, `parity`, `calving_date`, `milk_305_kg` (+ `site` при нескольких площадках).
  - Горизонт: **не прогноз “в будущее на N месяцев”**, а оценка/скоринг по доступным лактациям и стандартная сопоставимость групп.
  - Гранулярность: **лактация** (одна строка = одна лактация животного).

- **Предпосылки по бизнес-логике**
  - Сравнение корректно только внутри **contemporary group**: площадка/ферма + период (год/квартал) + parity.
  - Рекомендации формируются на пересечении: QC-флаги + ML-скоринг + бизнес-правила (пороги/минимальные размеры групп).

- **Предпосылки по эксплуатации**
  - Batch-режим пересчёта: ежемесячно/ежеквартально (на пилоте) → затем возможно еженедельно.
  - On-prem хранение и выполнение; внешние вызовы допустимы только после согласования ИБ/юристов.

### 2. Методология 

#### 2.1. Постановка задачи

- **Основная задача MVP:** прогноз/скоринг продуктивности `milk_305_kg` на уровне лактации и построение ранжирования животных/лактаций внутри сопоставимых групп.  
- Тип задачи: **регрессия + ранжирование** (и последующая генерация рекомендаций как decision-support).  
- Дополнительная задача: **оценка качества данных (QC) и confidence** выводов модели.

##### Этап 1 — Подготовка данных (EDA + витрины/таблицы)

**1) Данные и сущности (целевые переменные и признаки)**

Целевая переменная (для MVP):
| Название данных | Есть ли данные в компании / у клиента | Требуемый ресурс для получения | Проверено ли качество данных |
|---|---|---|---|
| `milk_305_kg` (удой 305 дней, кг) по лактации | Обычно есть в СЕЛЭКС/1С/Excel; иногда только test-day | PO + DS + зоотехник клиента | EDA требуется на пилоте |
| `ECM/FPCM_305` (опционально) | Если есть жир/белок по лактации или test-day | DS + зоотехник | EDA требуется |

Признаки (минимум для MVP):
| Название данных | Есть ли данные в компании / у клиента | Требуемый ресурс для получения | Проверено ли качество данных |
|---|---|---|---|
| `animal_id` (стабильный ID) | Да (учетная система) | DS/аналитик данных + ИТ клиента | EDA требуется |
| `lactation_id` или ключ (animal_id+parity+calving_date) | Иногда | DS + ИТ клиента | EDA требуется |
| `parity` | Да | DS | EDA требуется |
| `calving_date` | Да | DS | EDA требуется |
| `birth_date` (для `age_at_calving`) | Часто | DS | EDA требуется |
| `farm_id` / площадка | Для холдингов — важно | PO/DS | EDA требуется |
| test-day ряд: `test_date`, `milk_kg`, `fat%`, `protein%`, `SCC` | Если ведут контрольные дойки/датчики | DS + ИТ клиента | EDA требуется |
| события (осеменение/болезни/выбраковка) | Опционально для расширения | DS | EDA позже (P1+) |
| погодные/THI (опционально) | Можно подтягивать извне | DS/DE | EDA позже |

**2) Результаты EDA (на суррогатном публичном датасете) и переносимые требования**

Публичный набор: `Dairy-Milkyield-Taenikon` (Zenodo), файл `lactperiod_5_150.csv`:
- 9 614 строк × 122 колонки, 60 животных (`EartagID`), 67 лактаций (`EartagID_LactNumber`), daily records, диапазон дат 2015-01-05—2022-07-03.
- Пропуски в основном в метео-колонках (до ~3.5%).
- Найдена лактация с **большим временным разрывом** (max gap 258 дней) при сохранении DIM 5–150 → требуется QC на непрерывность/логичность временных рядов.
- Удой: median ~32 кг/день, редкие IQR-выбросы (~0.07%).

**Переносимые требования к данным пилота (СНГ):**
- стабильные ключи: `animal_id`, `lactation_id`/составной ключ;
- корректные даты и логика событий: `birth_date < calving_date`, DIM не «скачет», нет неожиданных гепов;
- политика пропусков: где можно импутировать, где строку помечать как `WARN/BAD`.

**3) Процесс генерации/поступления данных (как это будет в пилоте)**

Пилотный поток (MVP):
1) Клиент выгружает CSV/XLSX из СЕЛЭКС/1С/Excel (или из доильного ПО) по шаблону запроса данных.
2) Мы выполняем первичную нормализацию (mapping колонок → наш стандарт).
3) QC-отчет: список ошибок/аномалий + рекомендации по исправлению учета.
4) Формируем витрины/таблицы для обучения/скоринга.

Регулярность:
- Пилот: разово + 1–2 итерации исправлений данных.
- Эксплуатация (после пилота): ежемесячно/ежеквартально (по циклу управленческих отчетов фермы).

**4) Если данных недостаточно — как решаем**
- Нет `milk_305_kg`: использовать test-day ряд для расчета 305-удоя (правила/аппроксимация должны быть согласованы с зоотехником и зафиксированы в методологии).
- Мало исторических лактаций: ограничить модель до «ранжирования внутри фермы» и/или объединять данные нескольких площадок (только при одинаковой методологии учета).
- Нет `birth_date`: модель работает, но в отчете показываем ограничение (без `age_at_calving`).

**5) Конфиденциальность / юридические аспекты данных**
- Данные о животных обычно не являются персональными, но являются **коммерческой тайной** хозяйства.
- Минимум документов/условий для пилота: NDA, договор услуг/НИР, согласование прав на производные результаты (модель/индексы), требования к контуру хранения (часто локально/в стране).
- Политика обезличивания: хранить `farm_id` как псевдо-ID, не публиковать названия хозяйств; доступ по ролям.

**6) Необходимый результат этапа 1**
- Согласованный и повторяемый **Data Contract** (шаблон выгрузки + словарь полей).
- QC-правила и отчет (OK/WARN/BAD).
- Учебная выборка (витрина) и пакет метаданных (описание источника/версии/дат).

##### Этап 2 — Подготовка прогнозных моделей (бейзлайн + основной MVP)

**2.1. Задача и постановка (ML)**
- Тип задачи: **регрессия** для прогнозирования продуктивности по лактации (таргет `milk_305_kg` или ECM/FPCM), плюс преобразование результата в **ранжирование** и decision-support списки.

**2.2. ML-метрики и функции потерь (и почему)**
- Основная метрика: **MAE** (кг) — устойчива к выбросам, интерпретируема для бизнеса (ошибка в кг молока).
- Дополнительно: **RMSE** (штрафует большие ошибки), **R²** (объяснимая доля дисперсии), **Spearman rank corr** (качество ранжирования).
- Лосс (обучение): MAE/Huber (робастность). При необходимости интервалов — квантильная регрессия (pinball loss).

**2.3. Схема ML-валидации (анти-утечки)**
С учетом специфики данных (животные, лактации, время):
- Разделение по **животным** (Group split по `animal_id`) — чтобы модель не «видела» ту же корову в train и test.
- Дополнительно/альтернатива: temporal split по `calving_date` (обучение на прошлых годах, тест на последних).
- Для пилота: минимум 1 hold-out тестовый период + k-fold (GroupKFold) внутри train для подбора гиперпараметров.
- Критический анти-лейк: признаки, доступные только после окончания лактации, **не включать** при сценарии раннего прогноза.

**2.4. Бейзлайн (контрольная точка, без сложной ML)**
Цель бейзлайна: быстро дать понятный результат и проверить ценность отчета.
- Индекс = нормированный `milk_305_kg` внутри «современной группы» (ферма + год/сезон отёла + parity).
- Метрики: сравнение распределений, стабильность ранжирования, доля животных в «верх/низ» кластерах.
- Риски: не учитывает часть факторов (возраст, условия содержания), чувствителен к «маленьким группам».

**2.5. Основной MVP (ML обязателен)**
Рекомендуемая MVP-модель:
- Алгоритм: градиентный бустинг по деревьям (CatBoost/LightGBM/XGBoost) или ElasticNet как интерпретируемая альтернатива.
- Признаки: parity, age_at_calving, seasonality, исторические лактации (если доступны), производственные группы/площадки, test-day агрегаты (если есть), флаги здоровья/событий (опционально).
- Выходы модели:
  - `y_pred` (ожидаемый удой),
  - `residual = y_true - y_pred` (отклонение),
  - `uncertainty` (опционально; например, через квантильные модели).
- Индекс продуктивности: комбинация `residual` + нормализация по contemporay group + флаги доверия.

**2.6. Анализ и интерпретация работы модели**
- Глобальная интерпретация: feature importance (gain/permutation).
- Локальная: SHAP (топ факторов для конкретной коровы/лактации) → напрямую в AI-отчет.
- Диагностика: ошибки по кластерам (parity, сезон, площадка), анализ «провалов» модели и причин.

**2.7. Риски и способы снижения**
- Малый объем данных у пилота → использовать простые модели, регуляризация, объединение данных по площадкам (при равных правилах учета).
- Лейбл-нойз (`milk_305_kg` рассчитан по разным методикам) → фиксировать метод расчета, проверка согласованности, в отчете указывать методологию.
- Data leakage → жесткое ограничение набора фич по моменту времени.
- Сдвиг распределения (смена кормления/управления) → мониторинг качества и регулярный пересчет.

**2.8. Необходимый результат этапа 2**
- Бейзлайн + ML-MVP модели обучены и валидированы.
- Зафиксированы целевые метрики качества (на пилотном наборе) и ограничения применимости.
- Подготовлены объекты для отчета: индексы, списки, объяснения, метрики, флаги доверия.

##### Этап 3 — Генерация AI-отчёта (LLM + правила + доказательная база)

**Задача:** превратить результаты QC + ML + бизнес-правила в читаемый отчет с рекомендациями (decision-support).

Входы:
- QC-метрики и список проблем данных,
- метрики качества модели и ограничения,
- таблица скоринга по животным/лактациям,
- объяснения (SHAP/importance),
- бизнес-правила (например, запреты на «жесткие» формулировки, required disclaimers).

Выход:
- `Performance Ranking Report` (executive summary + рекомендации + приложение с таблицами).
- (Опционально P1) `Breeding & Mating Plan (Pedigree)` — если есть родословная.

Контроль качества текста:
- шаблоны разделов + обязательные дисклеймеры;
- факт-чекинг: все числа/списки в отчете должны ссылаться на конкретные строки/агрегаты (чтобы LLM не «галлюцинировала»);
- словарь терминов фермы (под клиента).

##### Этап 4 — Подготовка пилота и бизнес-проверка результата

- Совместная с клиентом проверка: корректность списков «в приоритет/под наблюдение/кандидаты на выбраковку».
- Согласование: как часто выпускать отчет, кто утверждает решения, какие формулировки допустимы юридически.
- Ретроспектива: что улучшить в данных и в модели перед следующей итерацией.

##### Этап 5 — Инференс по итерациям (batch) и мониторинг (минимум для MVP)

- Режим: batch-расчет (ежемесячно/ежеквартально).
- Мониторинг: доля пропусков, drift по ключевым фичам, деградация метрик (если есть разметка), стабильность ранжирования.
- Логирование версий: версия данных, версия модели, версия шаблона отчета.



### 3. Подготовка пилота

#### 3.1. Способ оценки пилота

- **Дизайн пилота (предпочтительно):** параллельный прогон в 2–3 циклах (например, 2 месяца)  
  - цикл 1: baseline + ML, отчёты для сравнения, решения фиксируются вручную;  
  - цикл 2: ML+AI отчёт как основной, baseline — для контроля;  
  - цикл 3 (опционально): улучшенные данные P0/P1 → проверка роста confidence и стабильности ранжирования.
- Если доступно: сравнение площадок (A/B по площадкам) — одна площадка использует отчёт как основной, другая — «как обычно». Важно: фиксировать различия условий.

#### 3.2. Что считаем успешным пилотом

Формализованные метрики:
- **Операционные:** время подготовки отчёта ≤ 24–72 часа (в MVP с сопровождением).  
- **Adoption:** ≥ 2 прогона отчёта и ≥ 3 решения по спискам на цикл.  
- **Data quality:** снижение ERROR по QC в P0 (ID/даты/обязательные поля) между итерациями.  
- **ML quality:** Spearman на test не хуже бейзлайна и/или улучшение (цели уточняются после EDA).  
- **Business readiness:** директор принимает Executive формат и готов обсуждать условия коммерческого внедрения.

#### 3.3. Подготовка пилота

- **Вычислительные ограничения:**  
  - На MVP целимся в модели, которые обучаются и считают скоринг на обычном сервере/ПК за часы, а не дни.  
  - Если сложно оценить заранее — фиксируем «калибровочный прогон» на бейзлайне и простом ML для оценки времени/ресурса.
- **Ограничение сложности моделей:**  
  - Приоритет — интерпретируемость и устойчивость; сложные модели включаем только если дают явный прирост качества и проходят требования on-prem.
- **Пакет документов для старта:**  
  - NDA + Data Appendix (поля P0/P1), согласование on-prem контура, список ролей на стороне клиента (зоотехник/ИТ/ИБ).

### 4. Внедрение (для production систем, если требуется)

#### 4.1. Архитектура решения
- Batch pipeline в on-prem контуре: запуск по расписанию/по кнопке, генерация артефактов и отчётов.

#### 4.2. Инфраструктура и масштабируемость
- On-prem: локальный сервер/VM/выделенный ПК.
- Масштабирование на N ферм: стандартизация входных форматов, шаблонов и журналов запусков.

#### 4.3. Требования к работе системы
- SLA MVP: отчёт готов в течение согласованного окна после получения данных (на пилоте фиксировать реально достижимое).
- Надёжность: пайплайн должен падать с понятной диагностикой при ERROR (нет обязательных полей).

#### 4.4. Безопасность системы
- Минимум: контроль доступа по ролям, локальное хранение, журнал запусков и доступа к отчётам.

#### 4.5. Безопасность данных
- Персональные данные сотрудников не нужны и исключаются.  
- Коммерческая тайна: NDA + ограничение распространения артефактов.

#### 4.6. Издержки
- На MVP оцениваем издержки на вычисления эмпирически по пилоту (время обучения/скоринга/генерации отчёта).

#### 4.7. Integration points
- На MVP: файловый обмен (XLSX/CSV).  
- В будущем: интеграция с учётными системами через API/интеграторов — отдельная итерация.

#### 4.8. Риски
- Нестабильные выгрузки и низкое качество данных → компенсируем QC + UC-3 + регламенты.
- Блокеры ИБ/юристов → on-prem + пакет договорных приложений.
- Ожидание «магии» → строгие дисклеймеры + прозрачные метрики и ограничения.
